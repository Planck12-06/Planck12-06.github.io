JMM（Java Memory Model）

JMM 是一套规范，并非一块真实内存。 它定义了多线程环境下，共享变量如何被读写、线程之间如何通信，从根源上屏蔽硬件与操作系统的内存访问差异。

学习主线：

阶段 要回答的问题 对应内容
是什么 JMM 到底是什么 定义、目的、抽象模型
保证什么 并发安全需要哪些性质 原子性、可见性、有序性
为什么要它 为什么代码顺序会和执行顺序不一样 指令重排序
怎么约束 JMM 用什么手段约束 内存屏障、happens-before
怎么用 实际编码怎么写 volatile / synchronized / final

一、JMM 是什么

（一）定义

JMM 是一个抽象的概念，并不真实存在，它描述的是一组规则或规范。

这组规范定义了 Java 程序中各个变量（包括实例字段、静态字段、构成数组对象的元素）的访问方式。

注意：JMM 只关注共享变量的访问规则；局部变量、方法参数是线程私有的，不在 JMM 管辖范围内。

（二）为什么需要 JMM

语言 内存模型 问题
C / C++ 直接使用物理硬件和操作系统的内存模型 同一段并发代码在不同平台表现不一致
Java JMM 统一抽象 一套代码在各平台并发语义一致

JMM 的核心目标：

  • 屏蔽各种硬件和操作系统的内存访问差异
  • 确保 Java 程序在不同平台上达到一致的并发效果
  • 简化多线程编程，增强程序可移植性

一句话理解：JMM 是 Java 面向并发开发者的「跨平台契约」，让程序员不必关心底层是 x86 还是 ARM。

二、核心抽象模型：主内存与工作内存

JMM 规定了线程与内存的交互方式，抽象为两部分：

区域 归属 说明
主内存 所有线程共享 所有变量都存在这里
工作内存 每个线程私有 保存该线程使用到的变量的副本

核心规则：

  1. 线程对变量的所有操作（读取、赋值等）都必须在工作内存中进行
  2. 线程不能直接读写主内存中的变量
  3. 线程之间的通信（传值）必须通过主内存完成

重点：工作内存是 JMM 的抽象概念，并不等同于 JVM 的「虚拟机栈」；它对应的是CPU 缓存 + 寄存器 + 编译器优化的综合抽象。

（三）八种原子操作（JMM 底层约定）

JMM 定义了 8 种主内存与工作内存之间的交互操作：

操作 作用域 说明
lock 主内存 把变量标识为一条线程独占
unlock 主内存 释放锁定状态
read 主内存 把变量值从主内存传输到工作内存
load 工作内存 把 read 得到的值放入工作内存的变量副本
use 工作内存 把变量值传递给执行引擎
assign 工作内存 把执行引擎的值赋给工作内存变量
store 工作内存 把工作内存的值传输到主内存
write 主内存 把 store 得到的值写入主内存变量

记忆方式：read → load（读入）、use → assign（使用）、store → write（写回），再加上 lock / unlock。这 8 种操作必须成对、按序出现。

三、JMM 的三大特性

JMM 围绕 原子性、可见性、有序性 建立规则，用于解决多线程环境下共享变量的并发安全问题。

（一）原子性（Atomicity）

定义：一个操作或多个操作，要么全部执行且执行过程不被任何因素打断，要么都不执行。

JMM 的保证：

  • JMM 能保证基本类型变量的读取、赋值等基本操作具有原子性（如 int a = 1）
  • 不保证复合操作的原子性（如 i++，实际是「读 → 改 → 写」三步）

保证手段：

手段 说明
synchronized 通过 monitor 保证代码块原子性
Lock 显式加锁
AtomicInteger 等原子类 基于 CAS 实现
java.util.concurrent 工具 并发容器、同步器等

易错点：volatile 不保证原子性！volatile int i; i++ 依然是线程不安全的。

（二）可见性（Visibility）

定义：当一个线程修改了共享变量的值，其他线程能够立即得知这个修改。

为什么会有可见性问题：

  • 线程把变量读入工作内存（CPU 缓存）后，修改不会立即写回主内存
  • 其他线程读到的可能还是旧值（缓存中的副本）

保证手段：

手段 说明
volatile 写操作立即刷回主内存，读操作直接从主内存读，最强保证
synchronized 释放锁前把变量刷回主内存，获取锁时从主内存重读
final 构造完成后，正确初始化的 final 字段对所有线程可见
Lock 与 synchronized 类似

底层原理：volatile 通过内存屏障强制刷新缓存，具体见后文。

（三）有序性（Ordering）

定义：程序执行的顺序按照代码的先后顺序执行。

现实情况：

  • 单线程内看起来是有序的（编译器保证单线程的语义正确）
  • 多线程环境下，编译器和处理器可能进行指令重排序，导致实际执行顺序与代码顺序不同

保证手段：

手段 说明
volatile 通过内存屏障禁止特定重排序
synchronized 同一时刻只有一个线程执行，相当于串行化
happens-before 规则 JMM 的核心约束，判断操作是否可能重排

（四）三大特性速查表

特性 含义 volatile synchronized
原子性 不可分割 ❌ 不保证 ✅ 保证
可见性 修改立即可见 ✅ 保证 ✅ 保证
有序性 禁止重排序 ✅ 保证 ✅ 保证

核心记忆：volatile 保证「可见性 + 有序性」，但不保证原子性。这是面试中最常考的点。

四、指令重排序

（一）什么是重排序

指令重排序：编译器和处理器为了提升执行效率，在不改变单线程执行结果的前提下，对指令的执行顺序进行重新排列。

（二）三种重排序

类型 谁在做 说明
编译器重排序 JVM 的 JIT 编译器 不改变单线程语义前提下的优化
指令级并行重排序 CPU 现代 CPU 支持流水线，多条指令可重叠执行
内存系统重排序 CPU 缓存 / 写缓冲区 读写的可见性延迟导致「看起来」乱序

关系：这三种重排序都会遵守数据依赖性（有依赖的指令不会重排），但跨线程的共享变量之间没有这种约束。

（四）as-if-serial 语义

as-if-serial：不管怎么重排序，单线程程序的执行结果不能被改变。

这意味着：

  • 编译器、运行时必须遵守 as-if-serial
  • 存在数据依赖的操作不能被重排序
  • 因此单线程程序无需担心重排序问题，但多线程程序必须考虑

核心结论：重排序是单线程的安全优化，却可能成为多线程的安全隐患。

五、内存屏障（Memory Barrier）

（一）什么是内存屏障

内存屏障（也称内存栅栏，Memory Fence）是一条 CPU 指令，用于：

  1. 禁止屏障两侧的指令重排序
  2. 强制把写缓冲区的数据刷回主内存
  3. 保证内存操作的可见性

本质：它是 JMM 约束「有序性」和「可见性」的底层实现手段。

（二）四种基本屏障

屏障类型 作用
LoadLoad 确保 Load1 的数据装载先于 Load2 及后续 Load 指令
StoreStore 确保 Store1 的数据写回先于 Store2 及后续 Store 指令
LoadStore 确保 Load1 数据装载先于 Store2 及后续 Store 指令
StoreLoad 确保 Store1 写回先于 Load2 及后续 Load 指令（开销最大，兼具其他三种屏障效果）

StoreLoad 最重：它会清空处理器的写缓冲区，因此在 x86 架构下通常只有它需要显式插入。

（三）volatile 的内存屏障策略

JMM 为 volatile 规定了特定的屏障插入策略：

简化为 4 条规则：

位置 插入屏障
每个 volatile 写之前 StoreStore
每个 volatile 写之后 StoreLoad
每个 volatile 读之后 LoadLoad
每个 volatile 读之后 LoadStore

实测建议：实际执行时，x86 平台只保留了 StoreLoad 屏障（其余在 x86 中天然有序），但语义上必须满足上述 4 条规则。

（四）内存屏障的应用

应用场景 作用
volatile 通过屏障实现可见性与禁止重排序
synchronized 释放锁前的 StoreStore、获取锁时的 LoadLoad 等
CAS（原子类） 通过 lock 前缀指令 + 内存屏障保证原子性与可见性
final 字段 在构造函数末尾插入 StoreStore 屏障，保证 final 字段的初始化可见

六、happens-before 规则

（一）什么是 happens-before

happens-before 是 JMM 中定义两个操作之间可见性与顺序关系的核心规则。

如果操作 A happens-before 操作 B，那么：

  • A 的执行结果对 B 可见
  • A 的执行顺序在 B 之前（B 能看到 A 的影响）

重点理解：happens-before 不是指代码执行的实际时间先后，而是 JMM 保证的可见性约定。只要满足 happens-before 关系，即使实际执行时发生重排序，语义也必须等价。

（二）八条核心规则

规则 内容
1. 程序顺序规则 单个线程内，前面的操作 happens-before 后面的操作
2. 监视器锁规则 对同一个锁的 unlock 操作 happens-before 后续的 lock 操作
3. volatile 变量规则 对 volatile 变量的写操作 happens-before 后续的读操作
4. 线程启动规则 Thread.start() happens-before 该线程中的任何操作
5. 线程终止规则 线程中的所有操作 happens-before 其他线程检测到该线程终止（join() 返回）
6. 线程中断规则 对线程 interrupt() 的调用 happens-before 被中断线程检测到中断事件
7. 对象终结规则 对象的构造函数执行完成 happens-before 该对象的 finalize() 开始
8. 传递性 如果 A happens-before B，且 B happens-before C，那么 A happens-before C

记忆口诀：程序顺序、锁、volatile、线程启动、线程终止、中断、终结、传递。

（四）happens-before 与重排序的关系

  • happens-before 是上层语义规范
  • 内存屏障是底层实现手段
  • JMM 允许重排序，只要重排序不违反 happens-before 关系

理解要点：happens-before 保证了「可见性」，但不保证「原子性」。两个线程并发修改同一变量，仍需要加锁或使用原子类。

（三）final 的内存语义

final 字段在构造函数中完成初始化后，其他线程就能看到正确的值，无需同步。

实现原理：JMM 在构造函数末尾插入 StoreStore 屏障，禁止 final 字段的初始化被重排序到构造函数之外。

（四）编程建议

建议 说明
优先用 final 不可变对象天然线程安全
状态标记用 volatile 比锁轻量
复合操作用原子类或锁 不要指望 volatile 保证原子性
减少共享变量 把共享状态降到最少，是最根本的思路
优先使用 java.util.concurrent 已封装好内存语义，比手写更可靠

八、总结

（一）知识地图

模块 核心要点
JMM 定义 一组抽象规则，不是真实内存，屏蔽硬件差异
抽象模型 主内存（共享，存变量本身）+ 工作内存（私有，存副本）
八种操作 read/load、use/assign、store/write、lock/unlock
三大特性 原子性、可见性、有序性
指令重排序 编译器、指令级并行、内存系统三种；DCL 是经典坑
内存屏障 LoadLoad / StoreStore / LoadStore / StoreLoad
happens-before 八条规则，约束重排序、保证可见性
实现手段 volatile（可见 + 有序）、synchronized（三者全保）

（二）易错清单

  1. JMM 不是真实内存，是抽象规范
  2. volatile 不保证原子性，volatile int i; i++ 依然不安全
  3. 工作内存 ≠ 虚拟机栈，它是 CPU 缓存和寄存器的抽象
  4. 线程间通信必须通过主内存，不能直接读对方工作内存
  5. happens-before 不等于时间顺序，它是可见性约定
  6. DCL 单例必须加 volatile，否则可能拿到半初始化对象
  7. 重排序不影响单线程（as-if-serial），只影响多线程
  8. StoreLoad 屏障开销最大，是四种屏障中最重的
  9. final 字段安全发布的前提：构造函数中不能使 this 逸出
  10. happens-before 保证可见性，不保证原子性
