悲观锁

核心思想

悲观锁对并发冲突持保守悲观的态度：默认认为只要有多个操作同时访问共享资源，就一定会发生数据冲突。因此在操作数据之前，必须先加锁，确保同一时间只有一个操作能访问该资源，其他操作阻塞等待锁释放。

常见实现

数据库层面

关系型数据库中的行锁、表锁、读锁（共享锁）、写锁（排他锁）都属于悲观锁实现。最典型的是 MySQL InnoDB 引擎的 SELECT ... FOR UPDATE 语句，会对查询到的行加排他锁。

编程语言层面

Java 中的 synchronized 关键字、ReentrantLock 重入锁，本质都是悲观锁。

执行流程

  1. 操作共享资源前，先尝试获取锁
  2. 获取锁成功，执行读写操作
  3. 操作完成后释放锁
  4. 未获取到锁的线程 / 事务，进入阻塞等待状态，直到锁被释放

优缺点

类型 说明
优点
  • 数据一致性强，冲突发生时直接阻塞
  • 逻辑简单，容易理解和实现
  • 适合高冲突场景
缺点
  • 加锁 / 解锁有性能开销
  • 线程阻塞会降低系统吞吐量
  • 存在死锁风险
  • 长事务可能导致锁长时间占用

适用场景

  • 写多读少的业务场景
  • 数据竞争激烈的场景
  • 对数据一致性要求极高的场景
  • 例如：库存扣减、银行转账、订单状态变更

乐观锁与悲观锁对比

对比维度 悲观锁 乐观锁
核心假设 并发冲突一定会发生 并发冲突很少发生
加锁方式 操作前加锁，独占资源 操作前不加锁，提交时校验
冲突处理 冲突时阻塞等待 冲突时重试 / 失败回滚
性能开销 加锁解锁开销大，阻塞耗时 无锁开销，但冲突重试有消耗
数据一致性 强一致性，隔离性好 最终一致性，依赖重试机制
典型问题 死锁、锁饥饿、长事务锁占用 ABA 问题、高冲突下重试风暴
典型实现 SELECT ... FOR UPDATE、synchronized 版本号机制、CAS 原子类

两者最终都是为了保证并发环境下共享数据的正确性，但适用场景互补。悲观锁优先保证数据安全，牺牲部分性能；乐观锁优先保证系统性能，在低冲突场景下大幅提升并发吞吐量。
