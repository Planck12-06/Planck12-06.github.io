分布式锁

分布式锁是满足分布式系统或集群模式下跨进程可见并且互斥的锁。

在单机环境下，可以使用 synchronized、ReentrantLock 等 JVM 级别的锁来保证线程安全。但在分布式系统或集群模式下，多个 JVM 进程可能运行在不同的服务器上，此时本地锁无法保证跨进程的互斥访问，因此需要引入分布式锁。

一、三种实现方式对比

分布式锁的核心是实现多进程之间的互斥，满足这一点的方式有很多，常见的有三种方案，下表从多个维度对比其差异：

对比维度 MySQL Redis Zookeeper
互斥 利用 MySQL 本身的锁机制（如排他锁） 利用 SETNX 等互斥命令 利用节点的唯一性和有序性
高可用 好 好 好
高性能 一般 好 一般
安全性 断开连接自动释放锁 依赖锁超时时间，到期自动释放 临时节点，断开连接自动释放

二、三种方案的适用场景

第一节从横向对比了三种方案的差异，这里再从实际选型的角度简要说明各自适合的场景：

MySQL

利用 MySQL 的排他锁（如 SELECT ... FOR UPDATE）或唯一索引实现互斥。性能一般，但可靠性较好，适合已有 MySQL 集群且并发量不高的场景。

Redis

利用 Redis 的 SETNX 命令（或带 NX、EX 参数的 SET 命令）实现互斥。性能好、部署简单，是目前企业应用中最常用的分布式锁实现方式之一。但需要注意锁续期、可重入、主从一致性等问题。关于 SETNX 的手动实现，详见下文 第三节。

Zookeeper

利用 Zookeeper 的临时顺序节点实现互斥。每个客户端创建临时节点，编号最小的节点获得锁；释放锁时删除节点，后续节点按顺序获取锁。安全性高，断开连接后临时节点自动删除释放锁，避免死锁。

选型小结：并发量高、对性能敏感优先 Redis；对可靠性要求极高、可接受稍高性能损耗可选 Zookeeper；已有 MySQL 且改动成本高、并发不大时可用 MySQL 兜底。生产环境中，基于 Redis 的 Redisson 方案最为常见（见 第四节）。

三、基于 SETNX 手动实现分布式锁

1. SETNX 的互斥原理

SETNX（Set If Not eXists）的语义是「当 key 不存在时才写入」，天然具备互斥性：

  • 线程 A 执行 SETNX lock:order 1 → key 不存在，写入成功 → 获得锁
  • 线程 B 再执行 SETNX lock:order 1 → key 已存在，写入失败 → 抢锁失败

2. 最基础的加锁与释放（有缺陷）

这种最朴素的写法存在两个致命缺陷：

问题 说明
死锁风险 若加锁后服务宕机，未执行 DEL，锁将永久不释放
误删他人锁 若业务执行超时，锁已自动过期并被线程 B 持有，线程 A 执行完 DEL 会把 B 的锁误删

3. 改进版：原子加锁 + 唯一标识

为规避死锁，需要给锁设置过期时间；同时为避免误删，锁的 value 应使用唯一标识（如 UUID + 线程 ID），释放时只删自己的锁。

关键点：加锁与设置过期时间必须通过一条命令完成。若先 SETNX 成功、再 EXPIRE 之前宕机，又会回到死锁状态。因此现代写法是使用 SET key value NX EX seconds 一条命令，而非单纯的 SETNX（SETNX 本身不带过期参数）。

4. 仍未被解决的问题

即使做到上述两点，纯 SETNX 手写的锁依然存在以下短板，而这正是 Redisson 要解决的：

  • 不可重入：同一线程再次加锁会失败（Redisson 用 Hash + 重入次数解决）
  • 不可重试：抢不到锁只能自旋或放弃（Redisson 用 Semaphore + Pub/Sub 解决）
  • 锁续期：业务尚未执行完，锁已过期被他人抢走，互斥失效（Redisson 用 WatchDog 解决）
  • 主从一致性：主节点加锁后宕机未同步，新主无锁，他人又可加锁（Redisson 用 MultiLock 解决）

小结：SETNX 手动实现是分布式锁最基础、最直观的形态。理解了它的缺陷，也就理解了为什么在生产环境中更推荐直接使用 Redisson 这类成熟框架（见 第四节）。

四、Redisson 分布式锁

Redisson 是一个基于 Redis 的 Java 驻内存数据网格（In-Memory Data Grid）客户端，提供了功能完善的分布式锁实现。相比上文第三节基于 SETNX 的简单手写锁，Redisson 在底层思想上进行增强，系统性地解决了不可重入、不可重试、锁续期、主从一致性等问题。

Redisson 核心能力总览

特性 实现原理
可重入 利用 Redis 的 Hash 结构记录线程 ID 和重入次数
可重试 利用信号量（Semaphore）和 Pub/Sub 实现等待、唤醒与失败重试
锁续期 利用 WatchDog（看门狗），每隔一段时间（lockWatchdogTimeout / 3，默认 10 秒）重置过期时间
主从一致 利用 MultiLock 联锁机制，向多个独立 Redis 节点同时加锁，多数成功才算成功

(二) 可重试原理

当获取锁失败时，Redisson 不会立即放弃，而是通过信号量 + Pub/Sub 实现等待和重试。

流程说明

  1. 获取锁失败后，计算剩余等待时间（waitTime - 已耗时）
  2. 如果剩余等待时间 > 0，订阅 Redis 的锁释放通道（redisson_lock__channel:{lockName}）
  3. 通过 Semaphore 阻塞当前线程，等待被唤醒
  4. 当其他线程释放锁时，通过 Pub/Sub 发布释放消息，唤醒等待线程
  5. 被唤醒后再次尝试获取锁，直到成功或等待超时

(三) 锁续期原理（WatchDog）

WatchDog 是 Redisson 的看门狗机制，用于解决业务执行时间超过锁过期时间导致锁提前释放的问题。

触发条件

  • 未指定 leaseTime（或 leaseTime = -1）时，WatchDog 自动启用
  • 如果显式指定了 leaseTime，WatchDog 不会启用

运行机制

  1. 加锁成功后，默认设置锁的过期时间为 30000ms（30 秒）
  2. WatchDog 会启动一个定时任务，每隔 30000 / 3 = 10000ms（10 秒）执行一次
  3. 定时任务检查当前线程是否仍然持有锁，如果是则将锁的过期时间重置为 30 秒
  4. 当业务执行完毕调用 unlock() 后，WatchDog 停止续约

(四) 主从一致原理

问题背景

在 Redis 主从架构中，加锁操作通常在主节点（Master）上执行，然后异步同步到从节点（Slave）。如果主节点加锁成功后，还未同步到从节点就发生宕机，哨兵会从从节点中选举新的主节点。此时新主节点上没有锁信息，其他线程可以再次加锁成功，导致多个线程同时持有锁，破坏互斥性。

解决方案：MultiLock 联锁

Redisson 提供了 RedissonMultiLock，通过同时向多个独立的 Redis 节点加锁，只有当大部分节点加锁成功时，才认为加锁成功。

核心原理

  • 向 N 个独立的 Redis 节点同时发起加锁请求
  • 只有当加锁成功的节点数 >= N / 2 + 1（多数派）时，才认为加锁成功
  • 释放锁时，向所有节点发送释放请求

注意：这里要求多个 Redis 节点是独立的，没有主从关系，每个节点都是平等的。
