消息队列

本文以 优惠券秒杀 场景为主线，沿着 悲观锁 → 阻塞队列 → Redis Stream 消息队列 的方案演进路径，理解消息队列解决了什么问题、以及如何落地使用。

一、秒杀场景与方案演进概览

秒杀的核心挑战：高并发下防止超卖、保证一人一单，同时不让数据库被瞬时流量打垮。

围绕这一挑战，方案经历了三次演进：

方案 核心思路 主要缺陷
悲观锁（同步） 加锁串行化下单，数据库层校验 集群下锁失效、全流程同步阻塞，性能差
阻塞队列（JVM 异步） Lua 预检 + JVM 内存队列异步落库 宕机丢消息、无 ACK、有内存溢出风险
Redis Stream（最终方案） Lua 预检 + Redis 消息队列异步落库 实现略复杂，但可靠、可扩展

二、方案一：悲观锁实现优惠券秒杀

1. 实现思路

最直观的做法：在数据库层面完成所有校验（时间、库存、一人一单），用 悲观锁（synchronized，基于用户 ID 加锁）保证同一用户的并发请求串行执行，再通过事务方法落库。

2. 核心代码

3. 存在的问题

  • 集群失效：synchronized 是 JVM 级锁，集群部署时各实例各自加锁，一人一单被击穿（可升级为 Redisson 分布式锁，参见 分布式锁 笔记）
  • 同步阻塞：即使换成分布式锁，整个下单流程仍是同步调用——所有请求都要排队走数据库查重、扣减、插入，高并发下大量线程阻塞，吞吐量低

优化方向：把”校验”前移到 Redis（Lua 脚本原子判断），把”落库”变成后台异步执行——这就引出了异步下单思想。

三、方案二：阻塞队列实现优惠券秒杀

1. 实现思路

将同步流程拆为两段：

  • 主线程：执行 Lua 脚本，在 Redis 中原子完成时间/库存/一人一单校验，通过后立即返回订单 ID（响应极快）
  • 后台线程：从 JVM 内的 BlockingQueue 中取出订单，加分布式锁兜底后异步落库

2. 核心代码

3. 存在的问题

  • 宕机丢消息：订单存放在 JVM 内存中，服务宕机或重启，队列里未消费的订单全部丢失
  • 无确认机制：后台线程取出订单后若处理失败，消息无法重试（没有 ACK）
  • 不支持多实例：队列在单机 JVM 内，无法多个实例共同消费
  • 内存溢出风险：队列容量有限（1024 * 1024），秒杀流量过大时可能 OOM

根因：需要一个 独立于 JVM、可持久化、支持消费确认（ACK） 的队列——这正是 消息队列（Message Queue） 的定义。Redis 恰好提供了这样的能力。

四、消息队列知识：Redis 的三种实现

1. 什么是消息队列

消息队列（Message Queue），字面意思就是存放消息的队列。最简单的模型包含 3 个角色：

  • 消息队列（Broker）：存储和管理消息，也被称为消息代理
  • 生产者：发送消息到消息队列
  • 消费者：从消息队列获取消息并处理消息

生产者只需把消息交给 Broker，不必关心谁来处理、何时处理；消费者按各自节奏拉取处理，实现解耦与异步。映射到秒杀：主线程（生产者）把订单消息写入队列，后台线程（消费者）异步落库，削峰填谷、保护数据库。

Redis 提供了三种实现消息队列的方式：

方式 特点 适用场景
List 结构 基于 List 模拟消息队列 简单的任务队列
PubSub 发布/订阅消息模型 实时消息广播
Stream 完善的消息队列模型 生产级可靠消息队列（推荐）

2. 基于 List 结构模拟消息队列

使用 LPUSH 从一端写入、RPOP 从另一端读取，天然符合”队列”语义：

  • 优点：借助 Redis 持久化，消息可落地；满足有序性
  • 缺点：不支持广播；没有 ACK 机制，消费者取走消息后宕机则消息丢失

3. 基于 PubSub 实现消息队列

发布/订阅模型：发布者向频道发消息，所有订阅者都能收到：

  • 优点：支持多消费者广播，实时性高
  • 缺点：不支持持久化，Redis 重启或订阅者离线期间的消息全部丢失；消息堆积无上限；没有 ACK

4. 基于 Stream 实现消息队列（重点）

Stream 是 Redis 5.0 引入的专门的消息队列数据结构，弥补了 List 与 PubSub 的不足，是 Redis 中最完善的方案。

核心概念：

  • Consumer Group（消费组）：组内多个消费者共同消费，每条消息只被组内一个消费者处理（负载均衡）
  • last_delivered_id：消费组记录消费位置，避免重复消费
  • Pending List（待确认列表）：记录已投递但未 ACK 的消息，消费者宕机后可重新派发

优点：消息可持久化、可回溯；消费组支持负载均衡；有 ACK 机制，失败可重试；支持消息堆积管理。

5. 三种方式对比

对比项 List PubSub Stream
消息持久化 ✅ ❌ ✅
消息回溯 ❌ ❌ ✅
多消费者 ❌（竞争消费） ✅（广播） ✅（消费组）
消息确认（ACK） ❌ ❌ ✅
阻塞读取 ✅（BRPOP） ✅（订阅） ✅（XREADGROUP BLOCK）

结论：Stream 具备持久化 + 消费组 + ACK + pending-list 重试，恰好逐一化解阻塞队列方案的全部缺陷。因此秒杀最终方案选用 Redis Stream。

五、方案三：Redis Stream 实现优惠券秒杀

1. 实现思路

与阻塞队列方案相比，整体链路不变，只把”JVM 内存队列”替换为”Redis Stream”：

  1. 请求到达 seckillVoucher，执行 Lua 脚本：原子校验时间、库存、一人一单，并将订单消息写入 Redis Stream（校验 + 入队一步完成）
  2. 后台线程以消费组（g1/c1）从 Stream 读取订单，Redisson 分布式锁兜底，异步落库
  3. 处理成功后 XACK 确认；处理失败的消息留在 pending-list，由 handlePendingList 重试

2. 完整代码

3. 要点小结

  • 防超卖：Lua 脚本把”校验 + 写入 Stream”做成原子操作，判断与写入之间不会有并发缝隙
  • 可靠性：消息存于 Redis（可持久化），服务宕机重启后从 pending-list 恢复未确认消息，不丢单
  • 不重复：消费组记录消费位置 + XACK 确认 + Redisson 锁 + 数据库查重，多重保障一人一单
  • 高性能：主线程只与 Redis 交互即返回，数据库压力被削峰

六、三种方案总结

对比项 悲观锁 阻塞队列 Redis Stream
集群可用 ❌（JVM 锁） ✅ ✅
异步下单 ❌（同步阻塞） ✅ ✅
宕机不丢消息 — ❌（JVM 内存丢失） ✅（Redis 持久化 + pending-list）
消费确认（ACK） — ❌ ✅
多实例消费 — ❌ ✅（消费组）
数据库压力 大（全量请求打库） 小（Redis 预检 + 异步落库） 小（同左，且更可靠）

演进的本质：把”判断”不断前移（数据库 → Redis Lua），把”写库”不断后置（同步 → JVM 队列 → Redis Stream）。若业务对消息可靠性、事务、复杂路由有更高要求，可进一步引入 RabbitMQ、Kafka 等专业消息中间件。
